# Пр13. Аудит защищенности приложения на FastAPI

Две отдельные папки приложений: `vulnerable/` и `hardened/`.
В каждой есть `main.py` с политикой входа и свой `common.py` с маршрутами FastAPI, формой, sqlite и серверными сессиями. Код формы и инфраструктуры в этих файлах одинаковый, версии не импортируют друг друга. Меняется только проверка входа и хранение паролей.

## Файлы и архитектура

1. `vulnerable/main.py` - четыре ошибки с пометками V1-V4
2. `hardened/main.py` - четыре соответствующих исправления FIX V1-V4
3. `vulnerable/common.py`, `hardened/common.py` - одинаковые маршруты `/login`, `/profile`, `/logout`, форма и таблицы
4. `audit.py` - одинаковые атаки на обе версии и 14 дополнительных тестов
5. `requirements.txt`, `Dockerfile`, `compose.yaml` - окружение только в docker

Форма отправляет логин, пароль и csrf-токен. FastAPI принимает запрос, общий обработчик проверяет формат и размер, затем выбранная политика обращается к таблице `users`. При успехе создается серверная сессия. Таблица `sessions` хранит сессии, `attempts` - счетчики ограничений. В cookie передается случайный идентификатор, а не пароль или имя пользователя.

Имена cookies у версий разные, поэтому обычный переход между двумя портами не перезаписывает сессию соседней версии. Разные порты сами по себе не изолируют cookies; этот стенд не предназначен для совместного размещения с рабочими сервисами.

## Границы стенда

1. Только синтетические записи `admin`, `anna`, `boris` из `DEMO_USERS`
2. Никаких внешних целей, рабочих аккаунтов и реальных баз
3. Уязвимую версию не публиковать в интернете
4. Исправленная версия демонстрирует четыре исправления, но не заменяет полный аудит
5. http допустим только для локальной демонстрации; при развертывании нужен https

## Проверки без внешней сети

`TestClient` отправляет запросы непосредственно в FastAPI, не открывая сетевые сокеты. Это выполнение приложения, поэтому аудит запускается только на этапе проверки. Каждый сценарий получает отдельную временную базу. Проверяются ответы и доступ к `/profile`, а не только надпись об успехе.

```sh
docker run --rm --network none --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges --pids-limit 64 --memory 256m infosec-lab13-fastapi:local audit.py 2>&1 | tee fastapi-audit-results.txt
```

Сценарии можно запускать отдельно для плохой или хорошей версии, добавляя `--mode vulnerable` либо `--mode hardened`. Регрессионные тесты выполняются при полном прогоне без этого ограничения. Проверка срока блокировки меняет срок в тестовой базе, а не ждет минуту. Проверка сохранения счетчика пересоздает приложение на той же базе, но не заменяет проверку перезапуска контейнера.

## Демонстрация в браузере

```sh
docker compose up -d --build
docker compose ps
```

Одну версию можно запускать отдельно: `docker compose up -d vulnerable` или `docker compose up -d hardened`. Точки входа внутри контейнера - `python3 -m vulnerable.main` и `python3 -m hardened.main` с параметрами из `compose.yaml`.

1. Уязвимая версия: `http://127.0.0.1:18130`
2. Исправленная версия: `http://127.0.0.1:18131`
3. Обычный вход: `admin` / `Lab13-Admin-Pass!`
4. Инъекция в логине: `' OR 1=1 --`, пароль `wrong-password`
5. База исправленной FastAPI-версии хранится в новом volume `fastapi-hardened-data`; прежний volume не удаляется
6. Перед повтором атаки выйти из предыдущей сессии; блокировка действует 60 секунд

Если на этих портах еще работает прежний контейнер пр13, команда `up --build` заменит его новой версией. Сейчас запущенный ранее контейнер не изменялся.

Для остановки без удаления данных:

```sh
docker compose down
```

Порты публикуются только на loopback. Bridge-сеть допускает исходящие соединения, но приложение их не делает. Автоматический аудит запускается отдельно с `--network none`.

## Матрица исправлений

| Код | Плохая версия | Хорошая версия | Повторная проверка |
|---|---|---|---|
| V1 | Склейка sql | Параметр запроса | Тот же ввод и `/profile` |
| V2 | Открытый пароль | Argon2id со случайной солью | Чтение БД и вход с сохраненным значением |
| V3 | Нет счетчика | 5 попыток на ip + логин за 60 с, 30 на ip | 6 неверных паролей и правильный седьмым |
| V4 | Разные ошибки | Общий ответ 401 и проверка фиктивного хеша | `admin` и `nobody` с неверным паролем |

В сценарии V2 предполагается уже полученная копия учебной базы: веб-метода скачивания базы нет. Хеширование затрудняет офлайн-подбор, но не делает слабый пароль неуязвимым. Ограничитель не доказывает защиту от распределенного перебора. Равенство времени ответов отдельно не измеряется.
